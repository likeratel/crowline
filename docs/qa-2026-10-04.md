# Product QA — 2026-10-04

This is a dated assessment of the current working tree, not certification for every provider or operating system. The request covered commercial readiness, UI clarity, slow bulk project selection, and failure-path fixes. Existing accounts, tokens, selections, aliases, notification preferences and hidden execution keys were preserved. Automated evidence uses fictional data.

## Product changes

- Bulk selection now unlocks after confirmed local persistence. New selections refresh in the background; deselection does not issue a remote request. Repeated refresh requests share one in-flight operation. Failed saves still roll back and offer retry.
- Unrelated display/language/notification changes do not restart provider queries. Changed query inputs retain stale-result rejection. Removing one project preserves unchanged projects’ history cursors and pending state; changed account, target metadata and history-window inputs invalidate the relevant data.
- GitHub identity and temporary-token caching is restricted to a selected, fixed CLI identity for one operation. Mutable GitHub/Vercel sessions are revalidated and a detected account switch stops that operation. Failures are not cached; a new operation checks credentials again.
- First use starts with the connection action. Normal use prioritizes activities and monitored projects; healthy connection diagnostics and help no longer precede every activity list. Authentication instructions remain available on demand.
- Connection errors appear above long project lists. Login required, missing CLI, connection failure and stale verification results have distinct labels. Recovery opens the actual failing service/account. Another service’s timestamp cannot overwrite a failed account verification.
- Aliases retain explicit Save/Cancel/result feedback. Notification search has an accessible name. Controls retain the shared 36px size and spacing scale. An unconfigured updater cannot be enabled and does not offer a dead private-release link.
- Dashboard activity sections initially render 50 entries, with a local Show more action. Search covers all loaded records, including records beyond the rendered page. Filtering resets the page size. Grouping and target lookup no longer repeatedly copy a growing dictionary or scan every target for each record.
- A follow-up failure audit found two additional defects. A failed settings load previously fell back to writable defaults, allowing the next preference change to overwrite the original file. Settings load/validation failures now lock saving for that app session; a migration write failure retains the readable settings and also locks saving. Repairing the file or permissions requires a restart before writing resumes. Account, credential and sign-in mutations are blocked too. A persistent, localized recovery notice appears in the dashboard, settings and tray instead of first-use onboarding or a misleading GitHub issue.
- An initial event subscription failure previously recovered only the snapshot when Retry was clicked, leaving automatic updates disconnected. Retry now reacquires the subscription before accepting recovery, coalesces concurrent attempts and disposes listeners that finish after unmount.

## UI/UX follow-up

A further user-requested UI/UX review reproduced and corrected these problems:

- A service with no monitored project showed global totals and ordinary empty execution lists. It now explains how to select projects for that service, and its action opens the right service.
- Dashboard project counts, connected-account totals, pending queries and health messages now follow the selected service/account. Unmonitored accounts do not make the connection summary look unhealthy. Management links also preserve the filtered account, including additional accounts; explicit error recovery still takes precedence.
- Connection failures now expand automatically and put affected accounts first, exposing recovery without another disclosure click. Healthy details remain collapsed below the activity list.
- Search/account filters with zero results now show one neutral empty state and a clear-filters action. It preserves the current service, time range and saved display scope and returns keyboard focus to search. Long queries wrap without horizontal overflow.
- Both individual and bulk project-selection retries now use the original save-success follow-up: visible confirmation, one coalesced refresh for selection, no refresh for deselection, and duplicate-click protection. Repeated failure preserves the rollback and retry affordance.
- Notification permission lookup failures now show an inline error and a read-only retry instead of remaining on Checking. Diagnostic detail is collapsed; OS permission requests remain a separate explicit action.

Evidence: `tests/dashboard-context.spec.ts`, `tests/project-selection-retry.spec.ts`, `tests/notification-permission-recovery.spec.ts`, and synthetic screenshots `artifacts/ux-empty-{1080,720,360}.png`, `artifacts/ux-recovery-720.png`, `artifacts/ux-service-empty-720.png`. Independent review reproduced the original problems and passed the final fixes, including an additional retry failure and cross-service account-filter navigation. No new P1/P2 remained in this bounded pass. Real VoiceOver, Windows accessibility and first-time external-user usability testing remain outside this evidence.

The signed/notarized `-r3` native app was relaunched after this pass. Existing six targets and three completed account queries remained present. Native WebView checks confirmed service-scoped totals, no-results guidance, clearing filters while retaining the service and returning keyboard focus to search. The app was left on the All services dashboard; no persisted user settings were changed.

## Release boundary

The release workflow now requires explicit platform selection and signing configuration, validates platform trust and updater signatures before draft uploads, and fails on missing credentials or untrusted artifacts. Local direct-distribution verification is separate from updater configuration. See [release engineering](releases.md) for the exact candidate hash and Apple notarization evidence for the current packaged candidate. The Apple Silicon app and DMG both received Apple Accepted results, were stapled, and passed Gatekeeper; the mounted installer’s app matched the expected binary hash. The latest native app was restarted, and its three monitored GitHub/Vercel/Bitbucket accounts completed their queries with the existing six targets preserved. No user settings were changed during this native check.

General sale across all advertised services and platforms still needs:

1. Authenticated read-only acceptance tests for AWS and the additional providers, fresh/additional account sign-in, and current OS notification delivery. Existing GitHub/Vercel/Bitbucket checks do not prove all CLI versions or IAM configurations.
2. Windows installation, runtime, Authenticode signing and update tests; macOS Intel execution also requires its target environment.
3. An actual customer-accessible update/distribution channel. The private GitHub endpoint is not a public updater. Current local builds correctly report that automatic updates are unavailable.
4. Final user acceptance of the revised workflow and chosen launch support scope. Passing implementation QA is not user acceptance.
5. Native offline→online and sleep→wake recovery timing. Polling retries exist, but there is no dedicated wake/network-online trigger; synthetic failure tests do not establish real OS resume behavior.

No GitHub release was published, no source changes were pushed, and no customer account or real API payload was used as a test fixture.
